### 5.4 O1 — Offering Reference generation (acceptance properties, not a mandated mechanism)

`OfferingDefinitionService.establish` calls `_next_offering_reference()` → `f"OFFERING-{max_reference_sequence()+1:06d}"`. The `UNIQUE` constraint on `offering_reference` is the concurrency backstop; on `IntegrityError` the transaction is rolled back and the allocation retried (up to 5 attempts, then a clean 409). **No PostgreSQL `SEQUENCE`, no new DB object.** ~~`max_reference_sequence()` uses `func.substr` + `func.instr` + `cast(..., Integer)` — identical SQL on PostgreSQL and the SQLite test harness.~~ *(Corrected 2026-09-09 — this claim was false: `func.instr` compiles identically on both dialects, but PostgreSQL has no `instr()` builtin at all, so the query failed against production PostgreSQL — a Critical Gate 5 finding. See §16. Remediated: `max_reference_sequence()` now uses `func.substr(offering_reference, _REFERENCE_SUFFIX_OFFSET)` — a fixed, compile-time-known character offset derived from the shared `OFFERING_REFERENCE_PREFIX` constant, with no runtime search function at all — genuinely identical, portable SQL on PostgreSQL and SQLite. See §17/§18.)* Verified: `^OFFERING-\d{6}$`, system-assigned (caller-supplied `offering_reference`/`id`/`state`/`version` in the request body are ignored — not in the schema), monotonic and contiguous across successive establishes, unique.

### 5.5 O2 — `category_ref` optional / nullable, no taxonomy authority

## 17. Remediation (implementing session, 2026-09-09)

**Root cause:** `func.instr()` compiles to identical, dialect-unaware SQL text (`instr(...)`) regardless of target dialect — SQLAlchemy has no generic translation for it. SQLite defines `instr()` natively; PostgreSQL does not.

**Fix (smallest possible correction, within `TDS-C021 §9.3` latitude):** the offering-reference format is always the fixed `OFFERING-NNNNNN` shape this same service generates — no runtime search function is needed at all, since the numeric suffix always starts at the same, compile-time-known character offset. `max_reference_sequence()` now uses `func.substr(offering_reference, _REFERENCE_SUFFIX_OFFSET)`, where `_REFERENCE_SUFFIX_OFFSET = len(OFFERING_REFERENCE_PREFIX) + 2` (= 10, derived, not hardcoded). Two-argument `substr(string, start)` is standard and behaves identically on SQLite and PostgreSQL.

**Exactly four files changed** (verified: all four were already untracked WP-20 files before remediation began; no previously-tracked file was touched; no schema/migration/router/Pydantic-schema/frontend/authorization/audit/event-publish code was touched):
