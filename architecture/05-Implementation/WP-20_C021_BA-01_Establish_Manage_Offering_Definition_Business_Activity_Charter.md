## 2. Business Intent (Scope) — [A]

Verbatim basis, `CAP-001` line 75: *"Manage offerings."* Realized, at this BA's own minimum scope, per `ROD-C021` D4 (Option A + D): a persisted, **platform-global** Offering Definition record supporting **establish, list, and read** — realizing the `COM-001 §6` Offering Definition model at the data layer for the first increment, without any composition, publication, pricing computation, or downstream commercial integration.

**Scope, stated explicitly:**
- **In scope:** establish a standalone Atomic Offering Definition (canonical identity; system-assigned Offering Reference `COM-001-001` `PREFIX-NNNNNN`; canonical name; Product/Service classification; **optional** opaque `category_ref`; optional opaque `list_price_reference`; state `draft`); list Offering Definitions (platform-global, no tenant filter); read one Offering Definition by id; produce the first Authoritative Offering Definition Context and the stable Offering Reference for downstream consumption.
- **Out of scope:** see §19.

## 3. Trigger — [A]

Caller-invoked. A `PLATFORM_ADMIN` acts directly against C-021's own host (`AuthService`) — `POST /offerings`. There is **no cross-service write path, no write-fan-in, and no event-bus trigger** (contrast C-132) — the Offering Definition is established by a single, direct, authenticated administrative action.

## 6. Input Contract — [C, now built]

`EstablishOfferingDefinitionRequest` (`schemas/offering.py`): `offering_name` (str, 1–255, non-blank), `offering_kind` (`Literal["PRODUCT","SERVICE"]`), `category_ref` (`str | None`, ≤100 — **optional per `[RO DECISION]` O2**; if supplied, non-blank), `list_price_reference` (`str | None`, ≤100 — a reference string only, `[RO DECISION]` D6). `state`, `offering_reference`, `version`, `id` are **never caller-supplied** — the system assigns them.

## 7. Business Rules — [A]

- `offering_kind` is one of exactly two closed values, `PRODUCT` or `SERVICE` (`COM-001-021` Product↔Service axis) — the Digital/Physical secondary typology is excluded from BA-01 (`TDS-C021 §3`). CHECK-constrained.
- `state` is one of the closed set `{draft, published, retired}` (`COM-001-020`); BA-01 establishes and **only ever writes `draft`** (`ROD-C021` D7). CHECK-constrained. No transition is implemented.
- `offering_reference` satisfies the O1 acceptance properties — system-assigned, monotonic, `PREFIX-NNNNNN`, unique, concurrency-safe (`[RO DECISION]` O1). A PostgreSQL `SEQUENCE` is not mandated; the allocation mechanism is an application-level monotonic allocator (`OfferingDefinitionService._next_offering_reference`) backed by the `UNIQUE` constraint with an allocate-and-retry on collision.
- `category_ref` is an **optional**, opaque, non-authoritative reference (`[RO DECISION]` O2). No taxonomy authority, category management, `c021_category` table, taxonomy FK, or free-form taxonomy semantics is created.
- `list_price_reference` is an **optional** opaque reference **string only** (`ROD-C021` D6) — never a numeric or computed price; C-021 never rates, discounts, or executes a price.
- An Offering Definition is never itself a Subscription, a Customer/Account, an Entitlement/Feature, a computed Price, a Contract, or a Tenant (`PE-001-C021 §1.5`; `ROD-C021` D1/D2/D3). **C-023 Decision 3 is untouched and not fired** (§16, §19).
- No uniqueness/idempotency invariant is imposed on `offering_name` — two `draft` offerings may legitimately share a name (`TDS-C021 §9.5`).

## 10. Authorization / Accountability — [A, mechanism resolved]

This is the certified platform-global-administrative-object pattern (`C-003` Roles). ## 11. Organization / Membership Boundary (Tenant Isolation) — [A — structurally not applicable, substitute assurance provided]

The `c021_offering_definition` model carries **no `organization/tenant` column** (`[RO DECISION]` D8). `CLAUDE.md §21.4`'s Mandatory Tenant-Isolation Test Checklist is scoped to "endpoints whose underlying data model carries an organization/tenant boundary" — the C-021 catalog carries none, exactly as `/roles` does not. ## 12. Events / Outcomes — [C, now built]

`establish` calls `record_audit(action="ESTABLISH_OFFERING_DEFINITION", …, status=SUCCESS, actor_id=<person_id>, metadata={offering_reference, offering_kind, category_ref, list_price_reference, state})` — and `AuditStatus.DENIED` on the allocation-exhausted path — plus `publish_event("OFFERING_DEFINITION_ESTABLISHED", {…})`. `record_audit` / `publish_event` are `AuthService`'s existing structured-log primitives; **no new audit or event mechanism is designed**, and `publish_event` is **not** a real event bus (`IRA-C021 §16`). `list` / `read` are non-mutating and not audited (consistent with `role` / `c132` read paths). `SD-002 §6` Evidence applies per `COM-001-063` — satisfied by the `record_audit` trail.

## 14. Idempotency Expectations — [C]

No content-level idempotency: `(offering_name, offering_kind)` is not a natural key (`TDS-C021 §9.5`), so a double-submitted establish creates two distinct `draft` offerings, each with its own `offering_reference` — `COM-001 §6` names no invariant forbidding this. The only concurrency point requiring handling is `offering_reference` assignment, covered by the `UNIQUE` constraint + allocate-and-retry (`_next_offering_reference` / `establish`). Idempotency-mechanism selection is otherwise an implementation-time concern, no RO decision needed (mirrors `TD-152`).
