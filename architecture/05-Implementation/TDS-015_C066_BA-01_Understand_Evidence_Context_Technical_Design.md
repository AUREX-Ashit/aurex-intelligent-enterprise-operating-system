## 1. Purpose and Scope

Determines **how** a first, minimum-scope read/query capability against the already-real `evidence_registry` table would be built, if and when BA-01 is chartered — the mechanism, not the chartering decision. `IRA-C066` already established *that* a read-only gap exists (§3.3), *that* it is C-066's own genuine minimum first increment (§17), and *that* no new schema is required (§8). This document answers *where* the new read logic lives, *which* existing components it reuses, *what* its API/authorization/error contract is, and *which* design questions remain open for the Repository Owner rather than being silently resolved here.

**In scope:** the design of BA-01 (candidate) — Understand Evidence Context — strictly as `IRA-C066` §7 and §17 bound it: read-only access to `evidence_registry` rows the caller's own Organization owns, by identity or by filter, zero new migration, zero new table, zero new column.

**Out of scope, explicitly (mirrors `IRA-C066` §17's own "does NOT extend to" list, restated here for this document's own self-containment):**
- `SE-031` / `evidence_fusion_registry` (`AMD-013`) — a wholly separate, unimplemented table for AI-fusion scoring, not evidence storage or retrieval (`IRA-C066` §3.6).
- Any write, mutation, delete, or purge path against `evidence_registry` — remains WP-11's and WP-14's own exclusive province (`IRA-C066` §4); this design adds no method to `EvidenceRegistryRepository` beyond a read.
- Retention-floor enforcement (`SD-002-048`, `SE-051`), cross-object lineage (`SD-002-049`), or any other `SD-002` §6 rule a read-only BA does not touch (`IRA-C066` §13).
- Any Enterprise Experience / frontend component — undecided, `IRA-C066` §14 item 2, carried forward unresolved (§17 below).
- Reconciling `evidence_registry`'s own three-way logical-service-ownership ambiguity (`IRA-C066` §3.5) — does not block hosting BA-01 in `AIService` (the existing physical location, zero migration), but is not resolved by this design either.
- Correcting the `EvidenceRegistryModel` docstring's own "C-090's own future domain" framing (`IRA-C066` §3.2, §16 item 1) — an editorial item, not a design one.
- Assignment of a WP number, chartering of BA-01, or any implementation, migration, router, service, schema, or test file — none is created by this document (§23).

## 3. Business Intent / Business Outcome

Unchanged from `IRA-C066` §7: retrieve the current governed state of an Evidence record — by identity, or by a filtered criterion (`linked_entity_type`/`linked_entity_id`, `evidence_source`, `evidence_type`) — without establishing, mutating, or altering any object returned. Realizes `SD-002-040`'s "first-class... governed object" framing for the read side, and operationalizes `SD-002-044`'s "reusable across objects" principle by making that reuse queryable for the first time — today, reuse happens only through internal FK joins inside other WPs' own repository code (`IRA-C066` §3.3), never through a caller-facing capability.

Business/user question this closes (`IRA-C066` §6c, Executive Cognition Review): *"What Evidence exists for [an entity my Organization owns], and what are its own properties (source, confidence, verification status, provenance)?"* — a genuine Understand-stage question under `EXECUTIVE-COGNITION-REALIZATION-STRATEGY.md`'s own governing standard, not merely infrastructure exposure for its own sake.

## 5. Business Rules

Unchanged from `IRA-C066` §7, restated here as binding design constraints:
- Read-only. No `evidence_registry` row is created, mutated, transitioned, or deleted by any component this design describes.
- A caller never receives another Organization's own row — enforced structurally by the exact-match tenant filter (§4, §12), not merely by an authorization gate alone (defense in depth, mirroring `SD-002-109`'s "isolation is a storage/retrieval guarantee, not solely an access-control feature").
- No `evidence_registry` row is disclosed to exist (even a bare 403 "forbidden" that confirms the ID resolves to something) when the row belongs to a different Organization — the read path returns 404 in that case, not 403. **Citation correction (independent Technical Design Review of this document, remediated):** an earlier draft of this document attributed this decision to "the `TD-142`-class precedent" — independently re-verified against `TECH-DEBT.md` and found incorrect; `TD-142` concerns `discovery_provider_registry`'s own missing idempotency/natural-key mechanism (WP-14 BA-01), an unrelated gap. The actual, correct repository precedent is WP-12 BA-03's own cross-tenant-disclosure remediation ("BA-03 leaking an empty-`200` instead of `404` for a cross-tenant `conversation_id`," fixed during implementation, independently re-confirmed by both Gate 1 and Gate 2 — `WP-REG-001` WP-12 row) and the general Mandatory Tenant-Isolation Test Checklist probe `CLAUDE.md §21.4`(c) itself names ("an explicit probe of whether an unrelated tenant's identifier is accepted — if so, the endpoint SHALL be gated before submission"). This is a design decision this document makes explicitly (not left open), because it is a mechanism-level anti-enumeration choice, not a policy-level scope choice — only the citation was wrong, not the decision.

## 8. Data Model / Reuse Boundary

**No new migration, column, or table.** `evidence_registry` is reused exactly as it exists today (`IRA-C066` §8's own conclusion, re-verified directly for this design at §4 above). Every field BA-01 would expose is a direct field mapping of an already-physical column — no derived, computed, or joined data beyond the row itself (the single documented exception being the ordinary tenant-scoping predicate, which is a query filter, not a data-model change).

## 9. API / Service Contract Requirements (proposed design, not implemented)

Two new `GET` endpoints, mirroring `IRA-C066` §9's own proposed shape and `IRA-006`/WP-06's own delivered "read APIs against an already-existing table" precedent:

- **`GET /evidence/{evidence_id}`** — single-item. Returns `EvidenceResponse` (200) or 404 (not found, or found but belongs to a different Organization and the caller is not `PLATFORM_ADMIN` — §5's own anti-enumeration rule).
- **`GET /evidence`** — filtered list. Query parameters: `linked_entity_type` (optional), `linked_entity_id` (optional), `evidence_source` (optional), `evidence_type` (optional) — all independently optional, mirroring `IRA-C066` §7's own input contract. Returns `EvidenceListResponse` (200), scoped to the caller's own Organization (§12) regardless of which filters are supplied, **for every caller including `PLATFORM_ADMIN`** — a deliberate, conservative default pending a Repository Owner decision on whether `PLATFORM_ADMIN` cross-Organization listing is required at all, and if so, what selector mechanism the contract should carry (§10, §21 item 5). No target-Organization parameter is proposed here.
- **Response schemas (new, proposed):** `EvidenceResponse` — a direct field mapping of `EvidenceRegistryModel`'s own columns (§4), naming convention consistent with `schemas/search.py`'s existing `IndexConfigurationResponse` pattern. `EvidenceListResponse` wraps a list of `EvidenceResponse`, mirroring `IndexConfigurationListResponse`'s own shape.
- **New service layer:** a new `EvidenceContextService` (or equivalently named) class — no existing AIService service class owns Evidence read behavior today (`services/search_execution_service.py` and `services/search_index_service.py` are the only Search-capability services, neither touches `EvidenceRegistryModel`). This is an Extend of the `services/` directory pattern, not a Create of a new pattern — the class follows the same thin service-over-repository shape every existing AIService service already uses.
- **New router:** a new `routers/evidence.py`, registered via `app.include_router(...)` (§4) — **not** added to the existing `routers/search.py`, because `routers/search.py` is C-093's (Enterprise Search) own capability router; adding C-066 endpoints to it would blur capability ownership between C-093 and C-066, the same class of confusion `IRA-C066` §4 already warns against for the write paths. This routing separation is a design decision this document makes explicitly.

**Exact routing prefix/path naming remains an ordinary implementation-time detail, not a Repository Owner decision** — `IRA-C066` §9 already classified this as an "implementation-level, not constitutional" question (`IRA-C066` §6 table, Category C), and this design does not narrow that further than proposing `/evidence` as the natural default.

## 10. Authorization and Tenant-Isolation Model

**Established, not open:** `evidence_registry.organization_id` is `NOT NULL` (§4) — every row is strictly Organization-owned. The Mandatory Tenant-Isolation Test Checklist (`CLAUDE.md §21.4`) applies in full to any implementation of this design (§16).

**Remediation of independent Technical Design Review finding (substantial rewrite of this section):** the independent review of an earlier draft of this document found that the two options originally presented were not, in fact, a clean binary choice — `AuthService::require_matching_tenant_or_platform_admin` (`Backend/Services/AuthService/dependencies.py:58–91`, re-verified) authorizes a caller against an **explicitly supplied target-tenant header** (`X-Tenant-ID`, via `get_current_tenant()`), and BA-01's own endpoint contract (§9) carries no such header or parameter anywhere. A literal "verbatim mirror" of that function is therefore not mechanically compatible with BA-01's own designed shape without silently changing that contract. This section is rewritten to name three alternatives accurately, and — critically — to separate what is a *technical* judgment this document can make from what is a *policy* judgment the Repository Owner alone can make.

**Three candidate mechanisms (architectural options — the facts about what each would do, not a recommendation yet):**

- **Option A — reuse `AIService/dependencies.py::require_platform_admin` as-is (zero new code).** The mechanism every existing tenant-adjacent AIService router already uses (`conversation.py`, `discovery_providers.py`, `intelligence_candidates.py`, `knowledge_assets.py`, `search.py` — §4). Consequence: Evidence reads restricted to `PLATFORM_ADMIN` callers only. An ordinary member of the owning Organization could **not** read their own Organization's Evidence under this option.
- **Option B — extend `AIService/dependencies.py` with a new function mirroring `AuthService::require_matching_tenant_or_platform_admin` verbatim, including its `X-Tenant-ID`-header mechanism.** Consequence: this would require adding a header/parameter to BA-01's own API contract (§9) that is not currently part of this design — a change to the contract, not merely to the authorization layer beneath it. Architecturally available (an Extend of `AIService/dependencies.py`'s existing mirrored-from-AuthService pattern, per `CLAUDE.md §19.5`), but not compatible with §9 as currently specified without that contract change.
- **Option C (identified by the independent Technical Design Review, not in this document's original draft) — gate on `AIService/dependencies.py::get_current_claims` (authentication only, zero new code, already exists), and perform all Organization-scoping inside the repository query itself (§11), with an explicit `PLATFORM_ADMIN` branch in the service layer to permit cross-Organization access consistent with every other option's own treatment of `PLATFORM_ADMIN`.** Consequence: an ordinary authenticated caller in the owning Organization can read their own Organization's Evidence (no `PLATFORM_ADMIN` requirement); no new API contract element (no header) is introduced; less new code than either Option A's behavioral narrowing or Option B's contract change.

**Technical recommendation (this document's own judgment, not self-executing):** Option C is architecturally the cleanest fit for BA-01's own designed shape — it requires no contract change (unlike B), it does not narrow Evidence access to administrators only (unlike A), and per `CLAUDE.md §19.5`'s own Reuse-before-Create ordering it reuses more of what already exists (`get_current_claims`, already used platform-wide) than either alternative. This is a technical/mechanical assessment, not a decision — it is offered to inform, not substitute for, the policy decision below.

**Architectural consequence, stated separately from the technical recommendation:** whichever option is selected determines the *shape* of code to be written (a new dependency function in `AIService/dependencies.py` for Option B; a service-layer branch plus the existing `get_current_claims` for Option C; no new authorization code at all for Option A) — but does not, by itself, answer the question below.

**Repository Owner policy decision — NOT resolved by this document (elaborates, does not replace, `IRA-C066` §14 item 3, the same decision, not a new one):** may an ordinary member of the owning Organization read that Organization's own Evidence records at all, or is Evidence access restricted to `PLATFORM_ADMIN` (an administrator-only capability)? `IRA-C066` §14 item 3 already recorded this as unresolved, tying it explicitly to `SD-002-050`'s own human-governance framing and the fact that no distinct Evidence-reviewer persona is modeled anywhere in this repository. Nothing in `CAP-001`, `SD-002` §6, `SER-001`, or `ADR-023` (which governs a different table, `enterprise_knowledge_graph_registry`, and is cited here only as an authorization-pattern analogy, not as governing authority for `evidence_registry`) resolves this question — it remains, correctly, a Repository Owner decision. This document does not select Option A, B, or C on the Repository Owner's behalf. Once the Repository Owner answers the ordinary-member-vs-administrator-only question, the corresponding mechanism (A if administrator-only; C, or B with an accompanying contract change, if ordinary members are intended readers) follows directly and does not itself require a further separate decision.

**Anti-enumeration behavior (not open, §5):** regardless of which of the three options above is eventually selected, a foreign Organization's `evidence_id` supplied explicitly is rejected as 404, not 403 — the same probe class `CLAUDE.md §21.4`(c) requires and the WP-12 BA-03 cross-tenant-disclosure precedent already exercises (§5's own correction; not `TD-142`, which is unrelated).

**`PLATFORM_ADMIN` list-endpoint behavior — a related but distinct open question, raised by the independent Technical Design Review, not previously named in this document:** §9/§11 scope `GET /evidence` to the caller's own Organization unconditionally, with no parameter allowing a `PLATFORM_ADMIN` caller to list a *different* Organization's Evidence — unlike the single-item `GET /evidence/{evidence_id}` path, whose cross-Organization behavior for `PLATFORM_ADMIN` is already specified (§9, §13). No existing repository convention was found (§4) that resolves how a list-shaped endpoint should accept a target-Organization selector for a `PLATFORM_ADMIN` caller under Option A or Option C specifically (Option B's own `X-Tenant-ID` header, if selected, would incidentally supply one — but Option B is not selected by this document, §10 above). **This document deliberately does not invent an `X-Tenant-ID` header or any other target-Organization parameter to solve this** — doing so would silently expand §9's own API contract to solve a problem the Repository Owner has not yet been asked about. This is recorded as its own explicit, distinct Repository Owner decision (§21 item 5): whether `PLATFORM_ADMIN` cross-Organization listing is required for BA-01 at all, and if so, what the API contract's own target-Organization selection mechanism should be. Until decided, `GET /evidence` returns only the caller's own Organization's Evidence, for every caller including `PLATFORM_ADMIN` — a conservative, contract-consistent default that does not overstate functionality that has not been authorized.

## 11. Query / Filter Design

The list endpoint's tenant predicate is `EvidenceRegistryModel.organization_id == caller_organization_id` — an exact match, never `OR organization_id IS NULL` (§4's own distinction from `VectorIndexRegistryRepository`'s platform-wide-row pattern, which does not apply here because no platform-wide Evidence row is structurally possible under a `NOT NULL` column). Optional filters (`linked_entity_type`, `linked_entity_id`, `evidence_source`, `evidence_type`) are additive `AND` predicates layered on top of the mandatory tenant predicate — a caller can never widen a query beyond their own Organization by supplying or omitting any optional filter.

## 12. Transaction and Consistency Expectations

Pure read. A single `SELECT` per request, no explicit transaction boundary beyond the ORM session's own default read, no row locking, no multi-statement consistency concern. No write, so no commit/rollback semantics apply (contrast BA-05's own `TDS-013 §15`, which designs a write transaction — not applicable here).

## 13. Error Semantics

- **404** — `evidence_id` does not exist, or exists but belongs to a different Organization and the caller is not `PLATFORM_ADMIN` (§5, §10 — applies under either authorization option).
- **403** — the authorization dependency itself rejects the caller (exact trigger depends on which of §10's three options is eventually selected — Option A: caller lacks `PLATFORM_ADMIN`; Option B: caller's own tenant claim does not match the `X-Tenant-ID` header and caller lacks `PLATFORM_ADMIN`; Option C: caller is unauthenticated — `get_current_claims` itself already returns 401/403 for that case, and a mismatched-Organization caller receives 404, not 403, per §5's own anti-enumeration rule, not this status).
- **400** — malformed query parameter (e.g., a non-UUID `linked_entity_id`) — ordinary FastAPI/Pydantic type-coercion behavior, no bespoke validation logic proposed.
- **200** — success, including an empty `EvidenceListResponse` when no row matches the filters (not a 404 — an empty list is a valid, successful answer to a list query, distinct from a single-item lookup by identity returning nothing).

## 15. Testing Strategy

Mirrors `IRA-C066` §11's own proposed shape, following the existing two-organizations tenant-isolation test convention (§4 — a per-file `test_two_orgs_no_shared_row`-style pattern against `ORG_A`/`ORG_B` constants, not a shared fixture) — no new test framework, no new fixture pattern.

- Unit tests against the new repository read method(s): existence, filtering behavior (each optional filter independently and in combination), and the exact-match (never `OR NULL`) tenant predicate specifically.
- API tests against both new endpoints: 200 (own-Organization row, own-Organization list, empty list), 404 (nonexistent `evidence_id`; a real `evidence_id` belonging to a different, unrelated Organization), 400 (malformed filter), 403 (whichever §10 option is eventually selected).
- Mandatory Tenant-Isolation Test Checklist (`CLAUDE.md §21.4`), applied in full: (a) two distinct, unrelated Organizations seeded, no shared `evidence_registry` row; (b) a caller in one Organization cannot retrieve or infer another Organization's own Evidence row through either endpoint; (c) an unrelated Organization's `evidence_id` supplied explicitly to the single-item endpoint is rejected as 404, not disclosed via any other status code.
