## 5. Domain Model

Per the governing instruction's own required separation:

**A — Required for the minimum Establishment BA:**
- **Entitlement/License Anchor Context** — a resolved candidate Organization/Domain (Entitlement) and/or Membership (License) reference, non-authoritative (`PE-001-C023 §1.16`).
- **Authoritative Entitlement Context** / **Authoritative License Context** — the current, single, canonical fact per anchor (exactly one per Entitlement Anchor; exactly one per Membership Anchor).
- **Entitlement/License Change Intent Context** — establish-only, for this BA's own scope.
- **Proposed Entitlement Context** / **Proposed License Context** — the shaped, not-yet-committed candidate.
- **Resulting Entitlement Context** / **Resulting License Context** — the commit-produced, continuing outcome (no suspend/revoke outcome in this BA's own scope).
- **Entitlement identity** — Entitlement Type reference (an **already-recognized** type only, per `§9` below — never a newly-defined one in this scope).
- **License identity** — license type value (`FULL`/`LIGHT` at minimum, per the existing `C-007` enum; the four `URA-001-115` specialized types remain a distinct question, `§6` below).
- **Authority reference** — a reference to the Commit Authority instance that authorized the transition (`§7`).
- **Audit attributes** — actor, timestamp, authority used, prior/new state (`§16`).

**B — Required later for Consumption/Allocation (explicitly NOT designed here, Decision 4 deferred):**
- License Consumption fact, Allocation record, purchased-limit enforcement (`URA-001-116`).

**C — Required later for Catalog governance (explicitly NOT designed here, Decision 3 deferred):**
- Global Entitlement Type/Feature Catalog registry, catalog governance-authority mechanism.

**D — Future commercial/billing concerns (out of scope entirely for this design):**
- Billing linkage, Subscription-duration alignment (`§10`), Contract-derived source consumption.

**None of B, C, or D is implemented, designed in schema detail, or assumed necessary by this document.** They are named only to bound A precisely.

## 6. Ownership Boundaries (Decision 6 — mechanism-level resolution, Design Question 2)

Decision 6 (`§18.13`) resolved *which capability* owns what; it explicitly left the *mechanism* — how the two owned layers relate at the data level — for "a future C-023 Technical Design." This is that design.

**6.1 What is exclusively `C-007`-owned (unchanged, not touched):** `memberships.license_type` (`FULL`/`LIGHT`), the base classification fact, established at Membership creation (`MembershipService.establish()`) and mutable via the certified `BA-03` term-change path. This column, its migration, and its service code are **not modified, referenced by foreign key, or written to by any C-023 mechanism** in this design.

**6.2 What is exclusively C-023-owned:** the License governance layer — lifecycle (ACTIVE/SUSPENDED/REVOKED + derived EXPIRED), the four `URA-001-115` specialized license types `membership.license_type`'s own two-value enum does not cover, Granted License Capacity (where committed), the Entitlement Source Reference, and (once separately authorized, `§13`/`§14`) Consumption/Allocation and commercial/billing linkage.

**6.3 The relationship, answered per the governing instruction's own thirteen questions:**

1. **Is `membership.license_type` referenced directly?** Yes — by value, read-only, at the moment a C-023 License object is established or resolved. Never written to.
2. **Is there a new C-023 License object referencing the Membership?** Yes — recommended design: a new C-023-owned record (working name: `entitlement_license_registry`, mirroring the naming pattern of comparable existing registries — `approval_authorities`, `runtime_assignment_registry`), keyed by `membership_id` (a referenced UUID, not a hard cross-service database foreign key — consistent with `CLAUDE.md §8`'s "never access another service's database" and with `approval_authorities.object_id`'s own existing polymorphic-reference precedent for exactly this shape of cross-boundary reference).
3. **Identity/key relationship:** the C-023 License record's own authority key is the Membership Anchor (`membership_id`) — identical authority key to `membership.license_type` itself (`PE-001-C023`'s own Authoritative-Construct Analysis, unchanged), but a **separate row in a separate table**, not a column extension of `memberships`.
4. **What happens when Membership changes?** Out of this design's own scope in detail (Membership lifecycle is `C-007`'s own concern) — but the relationship is stated: the C-023 License record's own validity is conditioned on the referenced Membership continuing to exist and remain valid (mirrors `PE-001-C023 §1.16`'s own "invalidated only where the underlying Membership itself is invalidated (`C-007`'s concern, referenced)"). No C-023 mechanism establishes, changes, or terminates a Membership.
5. **How does Full/Light relate to the C-023 License governance layer?** `membership.license_type`'s own value is the **base classification fact** the C-023 License record's own lifecycle governs *on top of* — the C-023 record does not restate or duplicate the Full/Light value; it references it by reading the current `membership.license_type` at resolution/establishment time (an explicit design choice, not a duplication — see item 11).
6. **How are lifecycle states represented?** On the new C-023 License record only: `status` (`ACTIVE`/`SUSPENDED`/`REVOKED`, mirroring `AuthorityHolderStatus`'s and `VersionStatus`'s own established enum pattern in this codebase), `effective_from`/`effective_to` (deterministic EXPIRED is a derived read-time fact per `PE-001-C023 §1.17`, never a stored status value — mirrors `WP-03`'s own `compute_membership_authority_consequence()` precedent exactly).
7. **How is future Capacity represented without implementing Consumption now?** Not represented in this minimum design at all — no `granted_capacity`/`consumption`/`available_capacity` field is added to the schema sketch in `§5`-A. Deferred entirely to Decision 4's own trigger (`§14`).
8. **How is future billing linkage represented without implementing Billing now?** Not represented — no field added. A future, separately-designed extension, not sketched here (would risk inventing commercial semantics `PE-001-C023` itself does not yet authorize).
9. **What remains exclusively `C-007`-owned?** `memberships.license_type`, its own write path (`BA-01`/`BA-03`), and Membership existence/standing generally.
10. **What is exclusively C-023-owned?** The new License record's own lifecycle, effective period, Entitlement Source Reference, and (once separately authorized) Capacity/Consumption/billing fields.
11. **What must never be duplicated?** The Full/Light *value itself* — the C-023 License record does **not** carry its own copy of `FULL`/`LIGHT`; it references `membership.license_type` at read/establish time. Duplicating the value into a second column would recreate exactly the ownership ambiguity Decision 6 resolved. **This is the single most important design constraint this section establishes.**
12. **Migration implication:** **LIKELY, when this design is eventually implemented** — a new table (`entitlement_license_registry` or equivalent), no `ALTER` to `memberships`. Classified per `§19.4-A`'s and `§22.13`'s own prior findings (already established, not reopened): this is new-schema territory requiring `CLAUDE.md §18`/`§19.4`'s own STOP-and-report discipline at the point of actual creation — **this document proposes the design; it does not create the table, and a future implementation session must still perform its own STOP-and-report before running the migration**, exactly as `TDS-016` did for `tenant_registry`.
13. **Source of truth for each field/concept:** `membership.license_type` — `C-007`, `memberships` table. License lifecycle/effective period/Entitlement Source Reference — `C-023`, the new registry. Entitlement (type, scope, quantity) — `C-023` entirely (no `C-007` counterpart exists).

**Which service hosts this new table is itself an open question, disclosed rather than assumed.** No canonical document assigns C-023 to a specific microservice (`AuthService` currently hosts `C-001`/`C-002`/`C-003`/`C-004`/`C-006`/`C-007`; C-023 could plausibly extend it, given the shared `URA-001` primary specification and the Membership-anchor dependency, but no Repository Owner decision or ADR has made this assignment). **This design does not assume it** — the polymorphic-reference pattern in `§6.3` item 2 is chosen specifically because it works identically whether C-023 ends up co-located in `AuthService` or in its own service.

## 7. Authority Model (Decision 1 — mechanism-level design, Design Question 1)

**7.1 The specific C-023 Commit Authority instance.** Design recommendation: one `approval_authorities` row (`URA-001-41`, `C-003`/`WP-02`'s already-certified registry, per Decision 1), established once per Organization that has an active C-023 candidate BA — not a single platform-wide row, consistent with `approval_authorities.organization_id NOT NULL` for every scope.

**7.2 Identity/name.** Working name: `"Entitlement/License Commit Authority"` — free text in the existing `authority_name` column (no schema change required for the name itself, per `§19.4-A`'s own finding that `approval_authorities`'s own `authority_name` is already free-text and reusable as-is).

**7.3 Scope.** `scope_type = 'COMPANY'` (per the existing `ApprovalScopeType` enum) — one Commit Authority per Organization, matching `PE-001-C023`'s own Organization/Membership-scoped character (`§7`, already corrected, not reopened) and Decision 1's own explicit finding that this is *not* a platform-wide concern the way `C-040`'s `AI-001`/`AI-002` were.

**7.4 Relationship to Organization/Membership.** The Commit Authority instance is anchored to the Organization whose Entitlement (or whose Member's License) is being committed — `approval_authorities.organization_id` is the same Organization Anchor `PE-001-C023`'s own Entitlement construct already uses; for a License-only commit, the governing Organization is the Membership's own `organization_id`.

**7.5 Accountability point.** Design recommendation, not yet resolved: `approval_authorities` itself does not carry a "who currently holds this" field the way `authority_holders` does (a deliberate design difference between the two mechanisms, already established in `§19.4-A`/`§19.4-B`) — `approval_authorities` defines a *policy* (strategy, scope), not a *named holder*. The accountability point (which specific person or Group may exercise a `COMPANY`-scope, `ANY_ONE`-strategy Approval Authority) is therefore itself a **further, not-yet-designed question** this TDS discloses rather than silently resolves — most plausibly resolved via this codebase's own existing Group/Runtime-Assignment machinery (`URA-001-71`/`-74`, already-certified elsewhere in this repository) binding a Group to the Approval Authority, but **this binding mechanism is not designed here** and is named as an explicit open item (`§24`).

**7.6 How `ERB-C023-05` resolves the authority.** At Commit time, the design resolves the caller's own claimed identity against the currently-`ACTIVE` `approval_authorities` row for the target Organization + `authority_name = "Entitlement/License Commit Authority"`, evaluated per the row's own `approval_strategy` (recommended: `ANY_ONE` for the minimum scope — a single qualified approver suffices; `MAJORITY`/`SEQUENTIAL`/`ALL` remain available per the existing enum but are not recommended for a first, minimum-scope BA).

## 10. Lifecycle and Temporal Semantics (Design Question 4)

**10.1 What `PE-001-C023` itself establishes (confirmed directly, re-verified this pass):**
- Lifecycle states: `ACTIVE` (continuing), `SUSPENDED` (reversible — "a suspended Entitlement or License can be reactivated by governed action"), `REVOKED` (terminal — "never reactivated to the same grant... a new establishment is required," `PE-001-C023 §2.x`, Chapter 3 Quality/Guiding text, unchanged).
- `EXPIRED` is **never a stored status** — it is a continuously-recomputed, read-time-only derived fact evaluated against `effective_from`/`effective_to` at the moment of resolution (`ERB-C023-06`, `§1.17`/`§1.16`'s own "Effective Entitlement/License State Context" — "never persisted... never treated as a cached or permanently valid fact"). This mirrors `C-007`'s own already-certified `compute_membership_authority_consequence()` precedent exactly (§18.2, unchanged) — reused, not reinvented.
- `effective_from`/`effective_to` are **independent business dates set at Commit time**, per the establishing proposal — not derived, computed, or defaulted from any other capability's own dates.
- `URA-001-117`: feature Entitlements are time-bound and "automatically deactivate on expiry" — consistent with the derived-`EXPIRED` design above, not a contradiction.
- `URA-001-118`: trial/sandbox Entitlements carry their own start/end dates and usage limits — the same `effective_from`/`effective_to` shape, no separate "trial" construct needed in the minimum schema.

**10.2 What `PE-001-C023` does NOT establish — marked `PENDING CANONICAL BINDING / FUTURE GOVERNANCE DECISION`, per the governing instruction's own explicit directive, not invented here:**
- Whether License duration should align with Subscription duration. **`PE-001-C023` never states this rule.** Its own text treats a Subscription strictly as a non-authoritative "Entitlement Source Reference" (`BR-C023-02`, `C023-O02`: "without that source ever being treated as the entitlement itself") — this is evidence *against* an automatic duration-inheritance rule, but is not itself an affirmative "durations are independent" rule either. **PENDING CANONICAL BINDING.**
- Whether a License can outlive its triggering Subscription. **PENDING CANONICAL BINDING** — no source addresses this.
- Whether a License may begin before a Subscription (e.g., an administrative grant with no Subscription at all — which Decision 2 already confirms is a legitimate, severable path, `§6`/`§20.4`). This case is **structurally supported** (the administrative-establishment path requires no Subscription at all), but the *general* "License before Subscription, when both exist" temporal-ordering question remains **PENDING CANONICAL BINDING**.
- What happens when a Subscription is renewed or terminated. **PENDING CANONICAL BINDING** — `PE-001-C023` names only the receive-hand-off EX (`EX-C023-02`, explicitly out of this BA's own minimum scope, Decision 2) as the channel through which any such event would ever reach C-023; no rule states what a License should do in response.
- Whether additional License/Entitlement periods can be granted independently of any Subscription event. **Supported by the administrative-establishment path itself** (Decision 2) — each administrative Commit is its own independent business decision with its own `effective_from`/`effective_to`; no requirement to synchronize with any other capability's own dates.
- Whether dates are authoritative business dates or derived dates. **Resolved:** `effective_from`/`effective_to` are authoritative business dates, set at Commit time by the committing decision; only `EXPIRED`/currently-in-force status is a derived, read-time fact (`§10.1`).

**Per the governing instruction's own explicit caution: this design does NOT assume `C-020` must be implemented merely because temporal alignment may eventually matter, and does NOT treat Decision 2's own removal of `C-020` as a prerequisite as somehow implying an alignment rule exists.** Every Subscription-alignment question above is left exactly as open as `PE-001-C023` itself leaves it.

## 13. Organization/Tenant Relationship (Design Question 9)

**Organization** (`C-004`, closed, certified) is the Entitlement's own authority key, and — via Membership — the indirect anchor for License's own governing Organization (`§7.4`). **Membership** (`C-007`, closed, certified) is the License's own direct authority key. **Tenant** (`C-040`) is explicitly **not** assumed complete or required: `WP-16`'s own delivered scope is the minimal `(none) → PROVISIONED` fact (`organizations.tenant_id` populated once) — no broader Tenant-container resource model, no Tenant-level configuration surface distinct from Organization (`§9`, unchanged, not reopened). This design's own primary anchors (Organization, Membership) do not require any Tenant-container semantics beyond what `WP-16` already delivered. Where a future requirement needs genuinely Tenant-level (not Organization-level) scoping, that remains **Pending Canonical Binding**, exactly as `§9` already states — not expanded here.

**Membership anchor vs. License ownership, restated for clarity:** the Membership Anchor is the *key* License is filed under; it is not itself the *owner* of the C-023 License governance layer (`C-023` is, per Decision 6) — these are kept distinct per the governing instruction's own explicit requirement.

## 14. Transaction Model (Design Question 8)

Modeled directly on `MembershipService.establish()`'s own already-certified pattern (`WP-03`, reused, not reinvented):
1. **Validation** — target Organization and/or Membership exist (404 if not).
2. **Authority verification** — the caller satisfies the resolved Commit Authority (`§7`), evaluated before any write (403 if not — fails closed).
3. **Membership/Organization validation** — existence and (per `§13`) no additional Tenant-container check required for the minimum scope.
4. **Establishment** — insert the new C-023 License/Entitlement record inside a single database transaction, mirroring `MembershipRepository.create()` + `session.flush()`'s own existing shape.
5. **Audit recording** — `record_audit()` call immediately after successful persistence, mirroring `services/membership_service.py::establish()`'s own identical shape (reused, not reinvented, per `WP-14 BA-04`'s own remediation precedent for this exact omission class, `§23.5`).
6. **Failure handling** — any validation/authority failure aborts before any write; a persistence-layer failure (e.g., a race-condition duplicate) rolls back, mirroring `MembershipService.establish()`'s own `IntegrityError` → `rollback()` → 409 pattern exactly.

## 15. Idempotency/Concurrency (Design Question 8, continued)

**Duplicate prevention:** a uniqueness constraint on (anchor, "no more than one current Authoritative context") — `PE-001-C023 §1.16` itself already states "exactly one current Authoritative License Context per Membership Anchor" / "per Entitlement Anchor and entitlement type" as an **invariant** (`INV-C023-10`, unchanged) — the design reuses this already-specified invariant directly as a database-level `UniqueConstraint` (mirroring `memberships`' own `uq_membership_person_organization` precedent) rather than inventing a new one. **Race-window handling:** the same pre-check-then-create-then-catch-`IntegrityError` pattern `MembershipService.establish()` and every prior `WP-0X` Business Activity in this codebase already uses (reused, not reinvented). **Concurrency:** no additional locking beyond the unique constraint is designed — consistent with the minimum scope's own single-writer-per-anchor character; no concurrent-commit scenario beyond ordinary database-level race handling is identified as requiring additional design.

## 16. Audit Requirements (Design Question 10)

Per `record_audit()`'s own existing, already-certified mechanism (`observability.py`, reused across every prior Business Activity in this codebase, confirmed present and consistent — not assumed without verification): the minimum-scope Commit action must record, at minimum — the initiating `person_id`; the specific `approval_authorities` row (and, once designed, the Group/accountability point, `§7.5`) that authorized the action; the affected Organization and/or Membership; the License/Entitlement anchor and type established; the `effective_from`/`effective_to` dates; the resulting status; a correlation identifier (the new record's own `id`); and, on failure, the specific rejection reason (mirroring every existing `record_audit(..., status=AuditStatus.DENIED, ...)` call's own established shape in this codebase). This is a design requirement, not an implementation — no code is written here.

## 17. Frontend Boundary (Design Question 7)

Per Decision 5 (`§23.13`), **exactly two items, no more:**

**17.1 Establish License/Entitlement**

### 29.3 Candidate Analysis

**Candidate A — Direct Membership → Approval Authority binding (`membership_approval_authority`)**

Primary-source finding, not previously surfaced in this document: `Master_Technical_Architecture.md` fully specifies this table.

```sql
-- membership_approval_authority
-- PURPOSE: Assigns one or more approval authorities to a membership.
-- FK: membership_id -> membership_registry | approval_authority_id -> approval_authority_registry
CREATE TABLE membership_approval_authority (
    membership_id UUID REFERENCES membership_registry(membership_id),
    approval_authority_id UUID REFERENCES approval_authority_registry(approval_authority_id),
    effective_from TIMESTAMP WITH TIME ZONE,
    effective_to TIMESTAMP WITH TIME ZONE,
    PRIMARY KEY (membership_id, approval_authority_id, effective_from)
);
```

— and a Row-Level-Security policy (lines 4798–4803) scoping it to Organization via a join through `membership_registry.organization_id`, the identical indirect-scoping pattern this codebase already uses elsewhere (e.g., `ApprovalAuthority.domain_id` → `Domain`'s own Organization anchor). It also appears in the document's own schema-catalog summary (line 323): *"membership_approval_authority — assigns approval authorities to memberships."* This is independently corroborated by a pre-existing disclosure already in this codebase, predating this investigation: `approval_authority_repository.py::get_active_dependents()`'s own docstring names this exact table as *"Master Technical Architecture's canonical `membership_approval_authority` join table... the real dependent of an Approval Authority"* — confirming this investigation's finding matches an already-recorded, independent citation, not a new claim invented for this section.

Governance Test:
1. **Canonical?** Yes — explicit `CREATE TABLE` definition, explicit RLS policy, named in the schema catalog, all in `Master_Technical_Architecture.md`; independently pre-cited in `approval_authority_repository.py`.
2. **Implemented?** No — confirmed via `models/__init__.py`'s complete import list (no such model) and a repository-wide search (no migration references it).
3. **Organization-scoped?** Yes, by construction — not via its own `organization_id` column (it has none), but via RLS join through `membership_id → membership_registry.organization_id`, identical in kind to `ApprovalAuthority`'s own `domain_id → Domain`'s Organization anchor.
4. **Identifies the accountable actor?** Yes — `membership_id` names one specific Membership (Person + Organization + Role), the most precise accountable-actor binding available anywhere in this codebase for this purpose.
5. **Supports the Approval Authority strategy?** Yes for `ANY_ONE` — `TDS-C023 §7.6`'s own recommended minimum-scope strategy — one currently-effective (`effective_from`/`effective_to`-bounded) row for the caller's Membership against the target `approval_authorities` row is sufficient to satisfy `ANY_ONE`. `ALL`/`MAJORITY`/`SEQUENTIAL` would require additional, not-yet-designed vote-counting/sequencing logic layered on top of the same join table — genuinely open, but not blocking for the minimum scope.
6. **Requires new schema?** Yes, but not new *architecture* — implementing a SQLAlchemy model and Alembic migration that mirror an already-fully-specified canonical table exactly, the same class of act `authority_holders` (`TDS-017`) and `tenant_registry` (`TDS-016`) each already were: completing previously-disclosed canonical schema, not inventing it.
7. **Requires a new governance decision?** No — `IRA-C023 §19.13`'s Decision 1 (Option B) already named "reuse the existing Approval Authority mechanism" as the governing choice; `membership_approval_authority` is that same mechanism's own canonically pre-specified completion, not a competing or alternative mechanism requiring its own fresh decision.
8. **Requires repository-wide authorization infrastructure?** Yes — the table itself is generic `C-003`/`WP-02`-owned infrastructure (any capability using `approval_authorities` would depend on it), confirming (and sharpening, not merely repeating) `TDS-C023 §7.7`/`§24` item 3's own prior "possibly repository-wide" finding into a definite one.
9. **Conflicts with any certified capability?** No — additive only. Does not modify `approval_authorities`'s own certified schema/constraints (`WP-02` BA-03/07/08), `memberships`'s own certified schema (`WP-03` BA-01), `authority_holders` (`TDS-017`/C-040, an unrelated, deliberately Organization-independent mechanism), or `Backend/Runtime/AuthorizationEngine` (still M1-only, untouched).
