# Repository Owner Instruction

This instruction authorizes an Architecture Discovery exercise.

It is intended to determine whether the current repository architecture
requires architectural evolution.

The objective is NOT to redesign the platform.

The objective is NOT to invent new capabilities.

The objective is NOT to modernize documentation.

The objective is NOT to perform implementation.

The objective is to determine, strictly from repository evidence, whether
the existing architecture has naturally evolved to require refinement,
extension or consolidation.

Architecture shall be derived.

Architecture shall never be invented.

Repository evidence always takes precedence over assumption.

===============================================================================
CORE PRINCIPLES
===============================================================================

The repository is the single source of truth.

Every architectural recommendation shall be derived from:

• approved repository documents

• approved architecture

• approved capabilities

• approved implementation

• approved governance

No recommendation may contradict an approved architectural decision
unless repository evidence demonstrates that the previous decision is no
longer internally consistent.

Where possible:

Prefer evolution.

Avoid replacement.

Prefer extension.

Avoid duplication.

Prefer consolidation.

Avoid architectural proliferation.

===============================================================================
DISCOVERY PHILOSOPHY
===============================================================================

This exercise exists to answer one question only.

"Has the architecture naturally evolved to require a new architectural
concept?"

Do NOT attempt to create architecture because an idea appears useful.

Do NOT introduce concepts simply because they are modern.

Do NOT recommend new components because they are fashionable.

Instead:

Observe.

Analyse.

Derive.

Validate.

Only then recommend.

CONSTITUTIONAL OWNERSHIP VALIDATION (MANDATORY PREREQUISITE)
===============================================================================

*(Added Version 1.1, per Repository Owner Instruction "Constitutional
Ownership Validation Governance," following the Enterprise Intelligence
Exchange (EIX) Discovery and its own Constitutional Ownership Matrix.)*

-------------------------------------------------------------------------------
PURPOSE
-------------------------------------------------------------------------------

This section formalizes, as a distinct and named governance gate within
this methodology, a discipline that already exists, in substance, across
the repository:

`CLAUDE.md §12` ("Before creating any: service, API, entity, DTO, event,
table, utility — Search the repository first. Prefer: Extend → Refactor →
Reuse."), `CLAUDE.md §15` Golden Rule 1 ("Search before creating"), and
`CLAUDE.md §19.2`–`§19.3` ("Claude Code SHALL search the repository
before creating anything... Creation is always the final option, never
the first") already make this discipline mandatory, repository-wide, for
every artefact type they name. The Constitutional Recertification
(CR-3.0) program that produced `COM-001`, `PLT-001`, `GRC-001`, `OPM-001`,
and `ONT-001` independently practiced the identical discipline in its own
Authoring Notes before writing a single principle ("Before authoring any
new constitutional construct, the repository was searched for an
existing owner" — `OPM-001`'s own Authoring Note; the same pattern
repeats in `ONT-001`). The Enterprise Intelligence Exchange (EIX)
Discovery and its own Constitutional Ownership Matrix (§20 below)
demonstrated this discipline at a scale and formality neither `CLAUDE.md`
§12/§19 nor any prior CR-3.0 Authoring Note had used before: a complete,
evidenced, per-responsibility matrix, independently validated against
five explicit criteria.

This section exists to close the one gap that discovery exposed: the
underlying discipline was already mandatory everywhere, but no single
place named it as a specific, artifact-producing procedure, scoped to the
six highest-weight decision types below. This section does not compete
with, relax, or restate `CLAUDE.md §12`/`§18`/`§19` — those remain the
universal, binding rule for every artefact `CLAUDE.md` already names.
This section adds the missing, reusable *procedure* — Constitutional
Ownership Validation — that Phase 4 (Architectural Consolidation) and
Phase 9 (Recommendation) of this methodology invoke whenever a Discovery
exercise's own recommended direction might otherwise be "create
something new" at one of the six trigger scales below, each of which
already requires a Repository-Owner-level decision under existing
governance (`ARCH-000 §12.4`/`§12.6` for a new Constitutional document;
`CAP-001 §3`'s domain-range reservation for a new Domain or Capability;
this repository's own established precedent, most recently applied to
"AI Marketplace," that creating any of the six requires "a
Repository-Owner-level governance decision" no discovery report makes
unilaterally).

Constitutional Ownership Validation orchestrates evidence-gathering; it
never itself decides, owns, or creates anything — consistent with
`OPM-001-001`'s own principle, "Orchestration, Not Ownership," applied
here to a discovery procedure rather than to a constitutional domain.

-------------------------------------------------------------------------------
MANDATORY SEQUENCE
-------------------------------------------------------------------------------

Constitutional Ownership Validation is a mandatory prerequisite gate
before any Architecture Discovery exercise (or any other repository
activity) may recommend:

• a new Capability

• a new Constitutional Architecture document

• a new Enterprise Domain

• a new Work Package family

• a new Enterprise Platform

• a new Enterprise Service

The gate SHALL follow this sequence, in order:

**Step 1 — Discover the proposed responsibility.**
State the responsibility precisely enough to be checked against evidence
— not a domain name, a single testable claim (per Phase 1's own
Problem Definition discipline).

**Step 2 — Identify every existing constitutional owner.**
Search every companion document the proposed responsibility could
plausibly touch, not only the one document that prompted the question.
The EIX Discovery's own failure mode, had it stopped early, would have
been checking only `EIA-001`; the responsibility was in fact spread
across `COM-001`, `PLT-001`, `GRC-001`, `URA-001`, `RTA-001`, `SD-001`,
and `DS-001` as well.

**Step 3 — Determine whether the responsibility already belongs to:**

• an existing Capability (`CAP-001`)

• an existing Constitutional Document (any Layer 1 document under
  `ARCH-000 §6`'s Architectural Ownership table)

• an existing Enterprise Service (`Backend/Services/*`, per `CLAUDE.md
  §8`)

• an existing Work Package (`WP-REG-001`, `WPR-001`)

• an existing Strategic Enhancement (`SER-001`)

**Step 4 — Determine whether extending an existing constitutional owner
is architecturally preferable to creating something new**, per this
methodology's own Phase 4 (Architectural Consolidation) and per
`CLAUDE.md §19.5`'s Reuse → Configure → Extend → Compose → Create order.
A responsibility that is horizontal (would apply identically to a
domain the proposal did not originally name) is evidence *for*
extension, per the EIX Discovery's own finding for BYOL, Identity
Federation, and Enterprise Intelligence SLA.

**Step 5 — Only if repository evidence proves no constitutional owner
exists anywhere** may a new Capability, new Constitutional Architecture
document, new Enterprise Domain, or new Work Package family be
proposed — and even then, this methodology's own Discovery Completion
and Repository Owner Decision sections govern what happens next; a
proposal is never self-executing.

DECISION CRITERIA
-------------------------------------------------------------------------------

A responsibility is **Already Covered** when an existing document's own
stated Domain Ownership (its "what this document owns" section, the
pattern every CR-3.0 document already follows) names it, or when it is a
direct instance of a construct that document already generalizes (e.g.,
BYOL as an instance of `URA-001`'s already-extensible License Type
model).

A responsibility requires **Extend Existing Constitutional Document**
when no document currently names it, but a document's own stated
boundary or an explicit Pending Canonical Binding already reserves the
space it would occupy (e.g., `COM-001-052`'s own reservation of Contract
clause/term mechanics for a future capability-level specification).

A responsibility requires **Future Capability Decision** only when no
document owns it, no document reserves a space for it, and creating an
owner would require a new `CAP-001` domain or capability ID — and only
when this is independently, not speculatively, evidenced (the "AI
Marketplace" finding was not produced by asking whether one might be
useful; it was found already stated, and already deferred, in
`ARCHITECTURE-EVOLUTION-STRATEGIC-ROADMAP.md`).

A responsibility requires **Future Work Package** when its architecture
is already complete and LOCKED, and only its implementation remains
unbuilt and already tracked (`SER-001`) — this is not a constitutional
gap and shall never be escalated to Step 5.

No other Required Action label may be used. Do not invent additional
actions.

-------------------------------------------------------------------------------
REPOSITORY OWNER CHECKPOINTS
-------------------------------------------------------------------------------

Constitutional Ownership Validation SHALL pause for explicit Repository
Owner input at exactly these points, mirroring the STOP-and-report
discipline `CLAUDE.md §17`/`§18`/`§19.4` already establish for
implementation:

1. **Before Step 1 begins** — the Repository Owner names the domain and
   objective (this methodology's own Domain-Specific Discovery section);
   Constitutional Ownership Validation never selects its own domain.
2. **After Step 5, only if it concludes no owner exists** — before any
   new Capability, Constitutional document, Domain, Work Package family,
   Platform, or Service is proposed, the finding is reported and the
   Repository Owner decides whether to authorize a Future Capability
   Decision, request further investigation, or decline.
3. **Before any constitutional document is amended** under a "Extend
   Existing Constitutional Document" outcome — extension of a LOCKED
   Layer 1 document remains governed by `ARCH-000 §12.4`/`§12.6`'s own
   Constitutional Lifecycle and Evolution process; Constitutional
   Ownership Validation identifies the extension point, it does not
   authorize the amendment.

No other checkpoint is required; between these three points, the
validation proceeds without requiring per-step approval, mirroring
`CLAUDE.md §21.5`'s own "one authorization executes one complete
exercise" cadence.

-------------------------------------------------------------------------------
ACCEPTANCE CRITERIA
-------------------------------------------------------------------------------

A Constitutional Ownership Validation exercise is complete and
acceptable only when:

✓ Every proposed responsibility has been checked against every
  plausibly-relevant existing document, not only the document that
  prompted the question (Step 2).

✓ A Constitutional Ownership Matrix has been produced, with exactly the
  columns this section's own worked example (§ EXAMPLES below) uses:
  Responsibility, Original Intent, Existing Constitutional Owner,
  Governing Document, Governing Capability, Current Repository Status,
  Evidence, Required Action.

✓ Every row's Required Action is exactly one of the four labels this
  section permits.

✓ For every responsibility, the five validation checks (owner exists;
  owner is correct; no duplicate ownership; no conflicting capability;
  no unnecessary evolution) have been verified, not assumed.

✓ Any horizontal gap has been explicitly tested for a correct extension
  point before any new-capability language is used.

✓ No new Capability, Constitutional document, Enterprise Domain, Work
  Package family, Enterprise Platform, or Enterprise Service has been
  created or proposed as already-decided — only ever as a finding
  requiring the Repository Owner's own further authorization (Checkpoint
  2 above).

EXAMPLES
-------------------------------------------------------------------------------

**Reference example — Enterprise Intelligence Exchange (EIX).** The EIX
Discovery (`EIX-DISCOVERY_Enterprise_Intelligence_Exchange_Architecture_
Discovery.md`) and its own appended Constitutional Ownership Matrix are
the canonical worked example this section formalizes. Fifteen proposed
responsibilities were checked; twelve were found Already Covered across
six different existing documents (`EIA-001`, `CAP-001`, `RTA-001`,
`SD-001`/`DS-001`, `COM-001`, `CMD-001`/`SD-002`/`ONT-001`, `PE-001`,
`SER-001`, the roadmap documents); two (AI Policy Engine, Multi-Agent
Orchestration) required Future Work Package, their architecture already
LOCKED and only their implementation outstanding; three (Bring Your Own
Licence, Identity/Credential/Trust Federation, Enterprise Intelligence
SLA) required Extend Existing Constitutional Document, each a horizontal
concern with a proven extension point in `URA-001` or `COM-001`; exactly
one (AI Marketplace) reached Future Capability Decision, and only because
it had already, independently, been found ownerless and deferred by
prior repository work, not because this exercise assumed a gap. The
Final Decision (Option 1, no architectural evolution required) was
reached only after every row passed all five validation checks — not by
inspection of the headline domain name alone.

**Illustrative counter-example (hypothetical, not a repository finding):**
a discovery that checked only `EIA-001` for an EIX-shaped question, found
no owner there, and proceeded directly to recommending a new Capability
would have failed Step 2 (it did not search `COM-001`, `PLT-001`, or
`URA-001`) and would not satisfy this section's Acceptance Criteria — a
new-capability recommendation reached without checking every
plausibly-relevant existing document does not meet Step 5's own
evidentiary bar, regardless of how confidently it is stated.
