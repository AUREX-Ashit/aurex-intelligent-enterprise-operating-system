### 4.1 `EX-C001-01`/`EX-C001-02` (`ERB-C001-01`) Exclusion — Independently Re-Verified Correct

`ERB-C001-01`'s own Entry Context (Chapter 3, independently extracted): *"An Authoritative Person Context (C-006)... and an Access Evaluation Outcome (C-002) confirming the requesting persona is permitted to provision a new Identity for that Person. Neither is created here — both are consumed as already-resolved inputs."* `EX-C001-01`'s own Context Required (Chapter 4) repeats this without qualification: *"An Authoritative Person Context (C-006); an Access Evaluation Outcome (C-002) for the provisioning action."* Neither carries any "where governance requires one" or similarly conditional hedge anywhere in either field — this is a materially different textual shape from `EX-C001-07`'s own Context Required (§4.4 below), and confirms `IRA-008 §4.1`'s characterization of this requirement as unconditional is accurate, not overstated.

`IRA-005 §12` was independently re-read at its own location: *"`WP-RTA-001` is not yet a usable Permitted/Denied consumer for WP-05... no real, production `TierResolver` implementation exists for any of `URA-001-76`'s five tiers, including Domain Permission — every resolver exercised anywhere in that Work Package's own test suite is a test-only stub."* `WP-RTA-001_Closure_Report.md §7` was independently re-read at its own location: *"Not production ready... 1. Zero real data connections exist. No production resolver has been written for any of the five tiers, including Domain Permission. 2. Zero real consumers exist..."* Both documents, read directly rather than through `IRA-008`'s paraphrase, confirm the same root cause and the same conclusion: no genuine, affirmative Permitted/Denied Access Evaluation Outcome is obtainable from this repository's own running code today. ### 4.2 `EX-C001-03`/`EX-C001-04` "Satisfied by Construction" — Substantially Correct

`models/identity.py:38-43` independently confirms `email: Mapped[str] = mapped_column(String(255), unique=True, nullable=False, index=True)`. `auth_service.py`'s `authenticate_user()` (read in full) performs `identity_repo.get_by_email(login_data.email)` — an exact-equality lookup that, given the uniqueness constraint, structurally cannot return more than one row. `EX-C001-04`'s third outcome ("Identity resolution conflict" — the authoritative source yields no unique, consistent association) is therefore correctly disclosed as structurally unreachable in this schema, not a gap requiring new code.

The resulting JWT claims (`person_id`, `identity_id`, `organization_id`, `membership_id`, `role_code`) match `EX-C001-03`'s own stated Context Produced ("An Authoritative Identity Context, handed to EX-C001-05... and to whichever capability the Person next engages") — every dependent router's own Entry Context precondition is satisfied by these same claims, confirmed by the platform-wide `get_current_claims()`/`require_platform_admin()` dependency pattern used identically across every certified prior Work Package.

**One gap independently identified, not disclosed by `IRA-008 §4.2`: see §4.3.**

### 4.3 New Finding — Login Does Not Re-Confirm `Person.is_active`, Contrary to `EX-C001-03`'s Own "Re-Confirmed" Requirement (Currently Dormant)

`EX-C001-03`'s own Context Required text states: *"the claimed Identity signal; the established Identity-to-Person association it deterministically matches; a re-confirmed Authoritative Person Context (C-006) for that association"* — "re-confirmed," not merely "previously established." Direct, full reading of `authenticate_user()` in `auth_service.py` confirms it queries only `Identity` (Step 1–2) and `Membership` (Step 3) — no query against the `Person` table, and no reference to `Person.is_active`, occurs anywhere in the method. `models/person.py` confirms `is_active: Mapped[bool] = mapped_column(Boolean, default=True)` exists as a real column. A repository-wide search (`grep -rn "is_active\s*=\s*False\|is_active=False"`) across `Backend/Services/AuthService` found no production code path anywhere that ever sets `Person.is_active = False` — the only occurrences are three test fixtures (`test_identity_service.py`, `test_identity_api.py`; a third, unrelated docstring reference in `test_organization_service.py`). `WP-08`'s own `identity_status_service.py`/`identity_recovery_service.py` are the *only* code in this repository that reads `Person.is_active` today, and neither writes it.

**Assessment:** this gap is real but currently dormant — since no capability in this repository can deactivate a `Person` today, `POST /auth/login` cannot currently authenticate a caller whose Person Context has actually become invalid via that specific field. It becomes live the moment any future capability (most plausibly a future `C-006` Business Activity) adds a "deactivate Person" mechanism, at which point the pre-existing, unmodified login flow would continue authenticating such a caller — silently contradicting `EX-C001-03`'s own "re-confirmed" requirement and `BR-C001-01`'s adjacent principle that Identity validity traces to a currently-valid Person Context. This is a pre-existing condition of the R-001 login mechanism (out of `C-001`'s own scope per the charter's §3, and unmodified by WP-08), not a defect WP-08 introduced — but `IRA-008`'s own "satisfied by construction" analysis (§4.2) asserts the existing mechanism realizes `EX-C001-03` without disclosing this specific, verifiable gap. Recommended as new Technical Debt (§8).

### 4.4 New, Most Significant Finding — `BA-02` Never Requests an Access Evaluation Outcome, in Tension With `BR-C001-03` (Chapter 7)

`PE-001-C001` v1.1 Chapter 7 (`7.2 Business Rules`), independently extracted and read directly, states:

> **`BR-C001-03`** — *"Every Identity establishment and governed recovery action SHALL request a current Access Evaluation Outcome from C-002; none SHALL be computed by C-001."*

This is unconditional — it names "governed recovery action" without qualification, and it is a Chapter 7 **Business Rule**, the specification's own most authoritative normative-statement class (distinct from, and textually stronger than, Chapter 4's per-EX narrative "Context Required" prose). `Contract 5.3` (Chapter 5) independently corroborates the same unconditional shape: *"Every C-001 Enterprise Experience that performs a governed action (establishment, recovery) SHALL request, and SHALL NOT compute, an Access Evaluation Outcome from C-002 for that action."* Both name "recovery" alongside "establishment" as the two governed actions this rule binds, with no carve-out for a self-service branch.

By contrast, `EX-C001-07`'s own Context Required text (Chapter 4) — the sole textual basis `IRA-008 §4.5` and `TD-100` cite for scoping BA-02 to skip an Access Evaluation Outcome for the self-service branch — reads: *"a currently valid Authoritative Person Context (C-006); an Access Evaluation Outcome (C-002) for the recovery action **where governance requires one**"* (emphasis reflects the actual conditional language present in the source). `ERB-C001-04`'s own Experience Flow narrative (governing `EX-C001-07`) likewise never mentions requesting an Access Evaluation Outcome for the recovery branch at all.

**Independent code verification:** `identity_recovery_service.py`'s `request_recovery()` (read in full) determines eligibility solely from `person_repo.get_by_id(request.person_id)` and `person.is_active` — no call to any `C-002` endpoint, resolver, or evaluation-request mechanism occurs anywhere in the method or anywhere else in `BA-02`'s call chain (`routers/identity.py`'s `recover_identity()` also makes no such call). `BR-C001-03`'s own "SHALL request... none SHALL be computed by C-001" is not satisfied even in the minimal, "request but do not require an affirmative result" sense the text's own second clause implies is sufficient — no request is made at all.

**This is not the same, already-disclosed gap as `TD-100`.** `TD-100` correctly discloses that the *administrator-initiated* recovery branch is excluded because a genuine, affirmative Access Evaluation Outcome cannot be obtained (the same root cause as `TD-102`/`§4.1`). This finding is different in kind: it concerns the *self-service* branch WP-08 actually built, and the gap is that no Access Evaluation Outcome is even *requested* for it — not that an affirmative result cannot be obtained. `WP-05`'s own minimum-scope `C-002` implementation already provides a real, callable `Unresolved`/`Deferred`-branch endpoint (`IRA-005 §12`: "BA-01 — Evaluate Access for a Governed Request: Unresolved and Deferred outcome branches only... full scope" for the surrounding BAs) — `BR-C001-03`'s own text requires only that the *request* be made, not that an affirmative result be obtained before recovery may be recorded; a request that resolves `Unresolved`/`Deferred` would already satisfy the rule's own literal text without requiring any new `C-002` capability beyond what `WP-05` already delivered.

**Assessment of severity and blocking status:** This reviewer assesses this as a genuine, unaddressed specification-conformance gap — `IRA-008` does not cite, quote, or reconcile `BR-C001-03` or `Contract 5.3` anywhere in its own §4.5 (BA-02 scoping) or §9 (`TD-100`) analysis, despite both governing exactly this question at a textually stronger level than the Chapter-4 prose `IRA-008` does cite. It is **not assessed as blocking this certification**, for the following reasons: (a) no unsafe, incorrect, or unauthorized outcome results from the current behavior — `BA-02` only ever creates a `PENDING` audit-trail-eligible record; no `Identity` is established, no credential is reset, no Access is actually granted or bypassed, and no test fails; (b) had the omitted request been made under `WP-05`'s own current minimum scope, its only possible result today is `Unresolved`/`Deferred` — a result `IRA-008`'s own design would still need to decide how to handle, and no evidence suggests it would have blocked the self-service case Community members can reasonably expect to succeed; (c) the remediation is narrow, well-scoped, and does not require any new `C-002` capability beyond what `WP-05` already built. This is judged categorically different from a `CLAUDE.md §19.8.5` "architectural defect" that must block the Business Activity Completion Gate outright (which would apply to, e.g., a defect that grants unauthorized access) — but it is a real Business Rule non-conformance in a *built*, not merely *excluded*, code path, and this reviewer recommends it be treated with more urgency than an ordinary Low/Medium Technical Debt item. See §8/§9 for the recommended disposition.

### 4.5 `BA-01`/`BA-03` — Independently Re-Verified Correct
