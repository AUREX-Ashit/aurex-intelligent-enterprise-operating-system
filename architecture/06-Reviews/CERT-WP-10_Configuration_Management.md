## BLOCKING FINDING

### Finding B-1 (High, blocking): `GET /configuration` accepts an `X-Tenant-ID` for an Organization the caller holds no Membership in, and returns that Organization's established Configuration — a cross-tenant data disclosure of the same class `TD-113` already names as a `CLAUDE.md §19.8.5` finding requiring remediation, not deferral.

**What was checked and how.** `routers/configuration.py`'s `resolve_configuration` (BA-01) derives `organization_id` solely from `middleware.tenant.get_current_tenant()`, i.e., from the client-supplied `X-Tenant-ID` request header, parsed as a UUID with no further validation (`middleware/tenant.py` lines 223–241: the header is checked only for presence and UUID well-formedness). The endpoint is gated only by `get_current_claims` (`dependencies.py`) — authenticated, any role, no PLATFORM_ADMIN requirement, and, critically, **no comparison anywhere between the supplied `X-Tenant-ID` and the caller's own JWT `organization_id` claim or their own `Membership` rows.** `configuration.py` is the only router in this codebase that consumes `get_current_tenant()` at all (`grep` confirms zero other call sites), so this is a new trust boundary, not an existing, already-accepted pattern extended.

**Empirical proof.** A from-scratch runtime probe (not adapted from the shipped suite, executed and then removed — not committed) was run against the actual `main.py` app via `TestClient`:

1. Seed `Organization B` and a `Person` ("Outsider") with **no `Membership` row anywhere in the database** — no relationship between Outsider and Organization B exists.
2. `PLATFORM_ADMIN`-role token establishes a `BRANDING`/`logo_url` Configuration override for Organization B (simulating Organization B's real administrator).
3. Outsider, authenticated as `ESG_MANAGER` (a non-admin role), calls `GET /configuration?facet=BRANDING` with `X-Tenant-ID` set to Organization B's UUID — a value Outsider has no claim to and no Membership backing.

Result: **HTTP 200**, body reflects Organization B's own established override (`"value": "https://org-b-secret-logo.example.com/logo.png", "source": "TENANT"`). Outsider successfully read Organization B's Configuration despite having zero relationship to Organization B.

**Why this is a real defect, not a false positive.**

- It directly contradicts the Business Activity's own stated Authorization Rule (`IMP-REPORT-WP-10` §BA-01, `IRA-010 §5`): "every caller resolves **their own tenant's** Configuration." The implementation resolves whichever tenant the caller names in a header, not "their own" — nothing ties the header to the caller's own claims or Membership.
- `CLAUDE.md §21.4(c)` (Mandatory Tenant-Isolation Test Checklist) states this exact scenario in terms that require it be closed before submission: "where a request accepts a foreign-object identifier not derived from the caller's own claims, an explicit probe of whether an unrelated tenant's identifier is accepted — if so, the endpoint SHALL be gated before submission, not left ungated pending a future audit to discover it." `X-Tenant-ID` on `GET /configuration` is precisely such a foreign-object identifier (an Organization identifier), it is not derived from the caller's own claims, and the probe above confirms it is accepted.
- The shipped `TestConfigurationTenantIsolation` class (`tests/test_configuration_api.py`) does **not** perform this probe. Its three tests confirm that data established under Organization A does not leak when Organization B is separately queried — a real and correctly-implemented repository-level isolation property (every `ConfigurationEntryRepository` query does filter by `organization_id`, independently confirmed by reading all four query methods) — but every test in that class reuses **the same synthetic `Person`** for both organizations' calls, without ever creating (or checking) a `Membership` row tying that person to either organization. The class proves "Organization A's data doesn't bleed into an Organization B query"; it does not probe "can a caller with no relationship to Organization B name Organization B and get its data back" — the exact question `§21.4(c)` requires be asked. `IMP-REPORT-WP-10`'s own claim that this checklist is satisfied is therefore not supported by what the checklist actually requires.
- This repository has direct, on-point precedent for exactly this defect shape. `TD-113` (`TECH-DEBT.md`) describes `POST /workspaces/classify-handoff-rejection`'s pre-remediation state — "the endpoint's own caller-supplied `membership_id` is never verified against the caller's own claims... any authenticated Person of any role, in any Organization, could learn another tenant's own Membership... status" — and states in its own text that this is not ordinary interim debt but "**the remediation** for a `CLAUDE.md §19.8.5`-class finding... found and confirmed empirically" by a V&V Audit, closed by gating the endpoint. `GET /configuration` has the identical shape (caller-supplied tenant identifier, unverified against claims, disclosing another tenant's data to an authenticated caller with no relationship to that tenant) and, per the repository's own precedent for this exact pattern, is a `§19.8.5`-class finding.
- `CLAUDE.md §19.8.5` states plainly: "Technical Debt SHALL NOT be used to defer... tenant isolation defects... Such issues SHALL be remediated before the Business Activity Completion Gate (§19.7) is satisfied." This finding is not eligible for deferral to Gate 2 as Technical Debt.

**What is not affected.** `POST /configuration` and `GET /configuration/entries` (BA-02, establish/list) are gated by `require_platform_admin`, and the resulting "any `PLATFORM_ADMIN` may act on any tenant" shape is the same already-disclosed, already-accepted interim gate this repository uses throughout (`TD-021`–`TD-025`, `TD-113`'s own gating precedent) — that is pre-existing, disclosed architecture, not a new defect, and is not part of this finding. The defect is specific to `GET /configuration` being genuinely open to non-admin callers while trusting an unverified, caller-supplied tenant identifier.

**Recommended remediation shape (not performed by this reviewer, per instruction to certify/report only):** the smallest-scope fix consistent with `CLAUDE.md §19.5`'s Reuse-first order is for `get_current_tenant()` (or a `configuration`-specific dependency layered on it) to verify the supplied `X-Tenant-ID` against the caller's own JWT `organization_id` claim (already present in every access token, per `tests/test_configuration_api.py`'s own `_access_token()` and `providers.tsx`'s own `setTenantIdProvider`, which already derives the header from that same claim client-side) — rejecting with 403 when they differ, mirroring `TD-113`'s own remediation shape (close the disclosure at the boundary, not invent a new authority model). This does not require a new entity, table, API, or permission — it closes an unchecked comparison against data already carried in the existing JWT claims.

## Findings Escalated to Gate 2 (V&V Audit) — Not Blocking

### Finding G2-1 (Medium): No database-level constraint enforces "at most one ACTIVE row per (organization_id, facet, key)" in the actual Postgres target, not only in the SQLite test engine.

`models/configuration_entry.py`'s own `ConfigurationLifecycleState` docstring and `ConfigurationManagementService.establish()`'s own module docstring attribute the absence of a uniqueness constraint to "SQLite (this repository's own test engine)... has no portable equivalent of the Postgres partial/functional unique index this would require" — implying Postgres *would* enforce it. Independently verified: the actual migration (`alembic/versions/2026_08_12_0900-c7e2b5a9f1d4_configuration_entry.py`) creates only a **non-unique** composite index (`ix_configuration_entries_org_facet_key`) — no partial/functional unique index is created for Postgres either. The invariant is enforced only by `ConfigurationManagementService.establish()`'s own read-then-write sequence (`get_active_tenant_override` → mutate → insert, no explicit row lock, no `SELECT ... FOR UPDATE`), which is vulnerable to a lost-update race under concurrent `POST /configuration` calls for the same `(organization_id, facet, key)`: two concurrent requests can both read the same prior-ACTIVE row, both supersede it, and both insert a new row at the same `version`, leaving two simultaneously ACTIVE rows for the same key — which `ConfigurationResolutionService._resolve_facet()` would then encounter via `get_active_tenant_overrides_for_facet()`'s dict comprehension (`{entry.key: entry for entry in ...}`), silently picking whichever the iteration order returns last, with no error. This is a real (if narrow-window) data-integrity gap, not merely a test-environment artifact as currently documented — the mitigating factor is `POST /configuration` requires `PLATFORM_ADMIN`, a narrow-population, human-driven, low-concurrency caller, not a widely-used endpoint. Per `CLAUDE.md §19.8.7`'s rubric, this is Medium (an internal completeness/robustness concern that does not defeat BA-02's stated Business Intent under expected usage, but should be closed — e.g., a Postgres partial unique index on `(organization_id, facet, key) WHERE lifecycle_state = 'ACTIVE'`, or a `SELECT ... FOR UPDATE` — before the endpoint is exposed to higher-concurrency, self-service callers).

### Finding G2-2 (Low, documentation accuracy): `TD-116`'s Technical Debt Register entry undercounts the Scope Hierarchy gap slightly.

Not a functional defect — `IRA-010 §4.8`/§6 correctly and consistently scoped WP-10 to Tenant+User tiers throughout; `TD-116` is an accurate, honestly-disclosed statement of that scope boundary. Recorded here only because Gate 2's own broader mandate includes exhaustive specification-conformance checking: `TD-116` states the Scope Hierarchy has "eight tiers... Region, Country, Enterprise, Business Domain, and Business Object have no existing entity" (5 named as unanchored) but `CMD-001 §12.6` names Global Platform, Region, Country, Tenant, Enterprise, Business Domain, Business Object, User — 8 total, of which Global Platform is deliberately never persisted (by design, not a gap) and Tenant/User are the two implemented — leaving Region, Country, Enterprise, Business Domain, Business Object (5) genuinely unanchored, which is what `TD-116` states. On recount this matches; no correction needed. Confirmed accurate, not escalated further.

## Independently Re-Verified as Correct

- **Business Object Eligibility (`CMD-001 §26.3a`).** Re-derived from the primary text, not the implementation's own conclusion: Step 1 (Independent Identity) — a `ConfigurationEntry` row is written by one BA-02 call and later read by identity in an unrelated BA-01 call; satisfied. Step 2 (Cross-Experience Reference Test) — BA-01 is "a construct retrieved, by identity, from a separately-invoked later Business Activity," the exact satisfying language `§26.3a` Step 2 uses; satisfied. Step 3 (Governed Lifecycle) — `CMD-001 §12.5` mandates Versioning/Effective Dating/Lifecycle State/Audit Trail as non-optional, and the model genuinely implements a real supersession lifecycle (`ACTIVE` → `SUPERSEDED`, `effective_to` set, prior row retained); satisfied. Result: eligible, matching `IRA-010 §6`/`ADR-019`'s own conclusion. The "one family, not five" registration-shape reasoning (identical identity structure, lifecycle, and resolution algorithm across the five facets) is sound and consistent with `ADR-015`'s own precedent for `AEO-000001`.
- **`CBOR-INDEX.md` registration.** `CFG-000001` row present, correctly attributed to `ADR-019`/`IRA-010 §6`. The incidentally-added `AEO-000001` row is correctly attributed to `ADR-015`/`IRA-005 §11` and is consistent with `ADR-019`'s own §Decision item 6 disclosure of why it was missing.
- **Authorization design.** `GET /configuration` (BA-01) is authenticated-only, `POST /configuration` and `GET /configuration/entries` (BA-02) are `require_platform_admin`-gated — confirmed directly in `routers/configuration.py`. This asymmetric design is correct **in intent** (every caller should resolve their own tenant; only admins establish) — Finding B-1 above is that the "own tenant" half of that intent is not actually enforced for the read path, not that the intended design is wrong.
- **`middleware/tenant.py` non-exemption.** `/configuration` is genuinely absent from the exemption list (confirmed by direct read of the full `if path in [...]` block) and `main.py` mounts `configuration.router` at `/configuration` (confirmed) — `X-Tenant-ID` is genuinely required for both `GET`/`POST /configuration`, matching the claim (though the header's *value* is not verified — see Finding B-1).
- **Tenant filtering at the repository layer.** Every one of `ConfigurationEntryRepository`'s four query methods (`get_active_tenant_override`, `get_active_tenant_overrides_for_facet`, `get_active_user_overrides_for_facet`, `list_active_for_organization`) filters by `organization_id` — no query path returns cross-organization rows once a correct `organization_id` is supplied to it. The defect in Finding B-1 is entirely at the boundary (which `organization_id` is trusted), not in the repository/query layer.
