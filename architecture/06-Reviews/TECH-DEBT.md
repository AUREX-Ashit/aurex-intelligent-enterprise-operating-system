# Technical Debt Register

**Governing rule:** CLAUDE.md §19.8 (Technical Debt Management)
**Scope:** Repository-wide — not scoped to a single Work Package or Business Activity.

---

## Purpose

This register captures non-blocking engineering observations raised during Independent Review that:

- do not justify failing Independent Review,
- do not require an Architecture Decision Record (ADR),
- do not require immediate remediation,
- are intentionally deferred to a future Business Activity, Work Package, or release.

Per CLAUDE.md §19.8.2, Technical Debt SHALL NOT exist solely within Independent Review reports, implementation reports, commit messages, or chat history — it is recorded here.

Per CLAUDE.md §19.8.3, once an item is recorded here, future Independent Reviews reference its ID instead of repeating the full observation, e.g.:

> Observation: Tracked as TD-001. No additional discussion required.

Per CLAUDE.md §19.8.5, Technical Debt SHALL NOT be used to defer architectural, security, data integrity, or tenant-isolation defects, failing tests, build failures, broken functionality, or mandatory compliance requirements. Every item below was accepted through Independent Review as non-blocking before being recorded.

### TD-113 — Detailed Entry

- **Title:** `POST /workspaces/classify-handoff-rejection` Gated on `PLATFORM_ADMIN` Only — Remediation for a Confirmed Cross-Tenant Membership-Status Disclosure
- **Category:** Security
- **Description:** The WP-09 Gate 2 V&V Audit found, and confirmed via a from-scratch, two-tenant runtime probe (Organization A / Person A / Membership A and an unrelated Organization B / Person B / Membership B, no shared row anywhere), that `POST /workspaces/classify-handoff-rejection`, as originally shipped in commit `d648150`, allowed an authenticated caller in Tenant A to learn Tenant B's own Membership status (`ACTIVE` vs. `SUSPENDED`, surfaced as `CAPABILITY_SCOPED_INSUFFICIENCY` vs. `INTEGRITY_SIGNAL`) by supplying Tenant B's own `membership_id` — no ownership or tenant check existed anywhere in the request path, and `/workspaces` is fully exempted from `TenantMiddleware`'s own `X-Tenant-ID` check. This is a `CLAUDE.md §19.8.5`-class defect (a tenant-isolation boundary weakened, per §19.8.7's own High-severity trigger, "even if no exploit is currently known") — structurally identical in shape to `VV-AUDIT-WP-05`'s own Finding F-02 (an unscoped Approval Authority lookup disclosing another tenant's data), which that Work Package's own V&V Audit rated High and non-deferrable.
- **Root Cause:** The endpoint's own purpose (classifying a hand-off reported by a dependent capability) means the `membership_id` in the request is not necessarily the caller's own — unlike BA-01 (`person_id` from claims) and BA-02 (`membership_id`/`organization_id` from claims), BA-03 has no JWT-derived anchor to check the request against. `IRA-009 §5`'s own claim that this Business Activity is "a self-referential action against the caller's own Membership/context" is inaccurate for BA-03 specifically (confirmed inaccurate by the Gate 2 V&V Audit) — the same mischaracterization that let this gap ship without a caller-ownership or persona-scoping check.
- **Impact (pre-remediation):** Any authenticated Person, any role, any Organization, could query the CURRENT/UNRESOLVED status of an arbitrary `membership_id` belonging to any other tenant. Remediated in the same commit this entry is raised in: the endpoint now requires `require_platform_admin`, closing the disclosure for any non-admin caller. Independently re-verified at Gate 4 (`CLAUDE.md §19.7b`), including a negative control confirming the pre-fix code (commit `d648150`) is genuinely vulnerable and the post-fix code (this commit) is not.
- **Severity:** Low, **for this entry** — the disclosure itself (the `§19.8.5`-class defect) is closed by the `PLATFORM_ADMIN` gate; what remains open and tracked here is the *interim* nature of that gate, the same class of gap `TD-021` through `TD-025`/`TD-031`/`TD-034`–`TD-036`/`TD-039`/`TD-042`/`TD-079` already track repeatedly across this repository (no persona-specific, enforceable claim exists in the seeded role catalog for any capability-specific participant, pending `ADR-002` acceptance).
- **Status:** Open
- **Target Resolution:** A persona-specific, dependent-capability-scoped authorization model for `C-008` hand-off classification (a future, separately-scoped Business Activity or architecture amendment), followed by a persona-specific authorization dependency replacing `PLATFORM_ADMIN` for this endpoint — same resolution shape as every other entry in this same class.
- **Owning Work Package:** WP-09 — Workspace Management (C-008)
- **Related Business Activity:** BA-03 — Classify Workspace Hand-off Rejection (`EX-C008-11`)
- **Source:** WP-09 Gate 2 V&V Audit Finding 2 (from-scratch, two-tenant runtime probe); remediation independently re-verified at Gate 4
- **Resolution Criteria:** A persona-specific authorization dependency, scoped to legitimate dependent-capability callers, replaces the `PLATFORM_ADMIN` gate, with a corresponding test.
