## 3. Empirical Probes (From-Scratch, Not Adapted From the Shipped Suite)

All seven probes live in `Backend/Services/AIService/tests/_vv_probe_wp12.py`, run via:
```
cd Backend/Services/AIService
PYTHONCASEOK=1 python tests/_vv_probe_wp12.py
```

(`PYTHONCASEOK=1` is an unrelated, pre-existing Windows-Python-on-this-machine workaround for this repository's own `Config/` directory casing versus the `config.settings` import — not a WP-12 defect; the identical workaround is already documented in `_vv_probe_wp11.py`'s own header.)

Each probe builds its own fresh database (in-memory or temp-file, as the defect class under test requires) and its own `httpx.AsyncClient` + `ASGITransport`, mirroring `conftest.py`'s own pattern but independently constructed — none import fixtures from it.

### Probe 1 — Cross-tenant adversarial probe, all four endpoints, fresh organization IDs and payloads

Fresh `ORG_ALPHA`/`ORG_BETA` UUIDs (never appearing in `tests/test_conversation.py`) establish a Conversation and one Interaction under `ORG_ALPHA` carrying an identifiable secret string (`"ORG_ALPHA_CONFIDENTIAL_STRATEGY_STRING_74123"`). `ORG_BETA` then attempts `close`, `POST .../interactions`, and `GET .../interactions` against `ORG_ALPHA`'s own `conversation_id`.

**Result: no isolation defect.** All three cross-tenant attempts correctly return `404` (existence not disclosed, per `TDS-012`'s own design and `tests/test_conversation.py`'s own precedent); the response body of the (denied) `GET` attempt does not contain `ORG_ALPHA`'s secret string. A second check (Probe 1b) confirms `ORG_BETA`'s own, unrelated `establish` call does not leak `ORG_ALPHA` content either. This independently re-confirms the incidental cross-tenant defect `IMP-REPORT-WP-12` discloses as already found-and-fixed during implementation (BA-03's original empty-`200`-instead-of-`404` leak) is genuinely fixed, not merely claimed fixed.

### Probe 2a — Deterministic reproduction of the `UNIQUE(conversation_id, sequence_number)` check-then-insert race (BLOCKING for Gate-5-readiness disclosure purposes; see §5 for severity reasoning)

Two independently constructed `AsyncSession` objects (`session_a`, `session_b`), against the same physical temp-file SQLite database, are manually interleaved to force the exact race window in `InteractionRepository.next_sequence_number()`/`.create_pending()`: both compute `next_sequence_number() == 1` (neither has committed yet), `session_a` commits `sequence_number=1` successfully, `session_b` then attempts the identical insert.

**Result: `session_b`'s insert raises `sqlalchemy.exc.IntegrityError: UNIQUE constraint failed: interaction_registry.conversation_id, interaction_registry.sequence_number`.** A second, independent AST inspection of `services/interaction_service.py` confirms the `create_pending()` call site inside `InteractionService.execute()` is **not** wrapped in any `try`/`except` (only the subsequent `complete()` call is, per the source's own visible structure) — so this `IntegrityError` propagates uncaught through `execute()`, the router, and (per §2's own confirmed absence of any `@app.exception_handler`) surfaces as a bare, undiagnosed `500`.

### Probe 2b — Best-effort realistic reproduction via `asyncio.gather` against the real ASGI app (HTTP layer, `raise_app_exceptions=False` — exactly what a real client, including the shipped frontend, would receive)

Eight concurrent `POST /conversations/{id}/interactions` calls fired via `asyncio.gather` against one Conversation, backed by a temp-file SQLite database (a `:memory:` database would not share state across independently-pooled connections the way production's own per-request session pattern does).

**Result: 1 of 8 succeeded (`201`), 7 of 8 failed with a bare `500 Internal Server Error`** (`sqlite3.IntegrityError: UNIQUE constraint failed`, confirmed via the captured `LoggingMiddleware` error log and a sampled raw response body — `'Internal Server Error'`, no structured detail). This is a genuine, real end-to-end reproduction through the actual API surface, not only the repository layer — confirming Probe 2a's finding is not an artifact of the deterministic-interleave harness.

**This is not `VV-AUDIT-WP-11`'s own Finding 1 recurring.** That defect (no `UNIQUE` constraint at all, `MultipleResultsFound` on an ordinary *sequential* re-establishment of an identical index name) permanently and irrecoverably broke two Business Activities for the affected resource, with no `DELETE`/rename path to recover. Here, the `UNIQUE` constraint **is** present and **does** its job — it is the only thing standing between this race and silent data corruption — but the losing request simply fails loudly and can be retried; the winning request, the Conversation, and every prior Interaction remain fully correct and uncorrupted. See §5 for why this changes the severity conclusion relative to Finding 1, while still being a genuine, previously-undisclosed defect worth registering.

**3a** (mirrors `conftest.py`'s own engine configuration exactly — `sqlite+aiosqlite:///:memory:`, no `PRAGMA foreign_keys` listener): inserted an `interaction_registry` row directly via `InteractionRepository.create_pending()` referencing a `conversation_id` that was never created. **The insert succeeded with no FK error.** Confirms the pre-existing, repository-wide `TD-096`-class gap also covers WP-12's own new FK.

## 5. Findings

### Finding 1 (Medium, Technical-Debt-eligible — new registration required before Gate 5, not a Gate 3/4 blocker) — Concurrent Interaction submission against the same Conversation crashes with an unhandled 500

**Description:** `InteractionRepository.next_sequence_number()` computes the next `sequence_number` via a `SELECT ... ORDER BY ... DESC LIMIT 1`, then `InteractionRepository.create_pending()` inserts using that pre-computed value — a check-then-insert pattern with no `SELECT ... FOR UPDATE`, no application-level mutex, and no retry. `models/conversation.py::InteractionModel` DOES declare `UNIQUE(conversation_id, sequence_number)` (confirmed physically present in the migration, §1) — this was TDS-012 §4/§9's own explicit, disclosed intent, "built in from the start... mirroring the `TD-128` precedent," and it correctly does its job: it is structurally impossible for two Interactions in the same Conversation to ever persist with the same `sequence_number`. What TDS-012 did not additionally provide — and what `TD-128`'s own text already flagged as the necessary follow-up for exactly this shape of gap — is application-level handling of the resulting `IntegrityError` when two callers genuinely race. `InteractionService.execute()` wraps only its subsequent `complete()` call in `try`/`except`; the `create_pending()` call itself is unguarded (confirmed by direct AST inspection, Probe 2a). No `@app.exception_handler` exists anywhere in `AIService` (confirmed, §2's own RTM row), so the `IntegrityError` surfaces to the caller as a bare `500 Internal Server Error` with no structured detail — empirically confirmed at both the repository layer (Probe 2a, deterministic) and the real HTTP layer (Probe 2b, `asyncio.gather`, 7 of 8 concurrent requests failed this way).

**Failure scenario:** Two `PLATFORM_ADMIN` callers with access to the same organization's Conversation (the write-path gate is role-based, not conversation-owner-scoped — any `PLATFORM_ADMIN` in the tenant may execute against any Conversation in that tenant, confirmed by `routers/conversation.py`) submit a turn against the same open Conversation within the same narrow race window — e.g., two admins collaborating in the same conversation from separate browser tabs, or a client-side retry after a slow/timed-out response resending the same logical request while the original is still in flight server-side. One request succeeds cleanly; the other receives a bare, unhelpful `500` and must be manually retried by the caller (the shipped frontend's `describeError()` would render this as a generic "Unable to reach the server" or an unstructured error banner, not a clear "someone else submitted a turn just now, please retry" message).

**Why this is materially different from `VV-AUDIT-WP-11` Finding 1 (which WAS `§19.8.5`-class, non-deferrable, blocking):**
- WP-11 Finding 1 was reachable through **ordinary, sequential, single-caller use** (two sequential `POST`s, no concurrency required) and **permanently, irrecoverably** broke two Business Activities for the affected resource (no `DELETE`/rename path existed to recover — a database administrator had to intervene directly).
- This finding requires **genuine concurrency** (confirmed empirically — sequential use, including the shipped frontend's own submit-button-disable-while-executing behavior confirmed by direct source read of `ConversationTurnComposer.tsx`/`useConversationManagement.ts`, cannot trigger it through the UI in a single tab) and is **self-healing**: the `UNIQUE` constraint guarantees no corrupted or ambiguous row is ever created; the losing request can simply be retried and will succeed (a fresh `next_sequence_number()` call recomputes correctly against the now-committed winner). The Conversation is not broken afterward — only the one losing request failed.

**Precedent-based severity determination:** This repository already adjudicated a materially identical defect shape — a check-then-insert race against a `UNIQUE`-constrained table, requiring genuine concurrency, producing an unhandled crash if triggered — as `TD-128` (`VV-AUDIT-WP-11_Remediation_Verification.md`, Gate 4), and classified it **Medium, deferrable**, explicitly reasoning: "real concurrent establishment of the identical index name by the identical caller is a narrow, low-probability scenario distinct from Finding 1's own fully-deterministic, ordinary-sequential-use reachability." Applying that same calibration here yields **Medium**, not High, under `CLAUDE.md §19.8.7`'s own rubric ("an internal completeness or robustness concern... that does not defeat the capability's stated Business Intent... but is expected to require resolution before the capability is exercised at production scale") — the losing request's failure does not defeat "manage AI interactions" as a Business Intent even for a disclosed subset of *ordinary* use, since ordinary single-tab use cannot reach it at all.

**Where this finding is more exposed than `TD-128`'s own scenario (disclosed, not smoothed over):** `TD-128` concerns a `PLATFORM_ADMIN` re-establishing an index — an infrequent, single-admin action. This finding sits on **every single Interaction submission**, for the lifetime of every Conversation, and is reachable by **any two distinct `PLATFORM_ADMIN` callers** in the same organization (not only the identical caller racing themselves), which is a meaningfully higher-frequency exposure surface than `TD-128`'s own. This asymmetry is flagged explicitly for the Repository Owner's own Priority determination (`CLAUDE.md §19.8.2`) — Severity (Medium, per the rubric applied above) and Priority are independent per `§19.8.7`'s own text, and this finding's higher plausibility of being *hit* argues for a nearer-term Priority even though its Severity classification, on the rubric's own terms, remains Medium rather than High.

**Suggested remediation shape (not prescribed — a future remediation session's own determination, consistent with `CLAUDE.md §19.5`'s Reuse → Configure → Extend → Compose → Create discipline):** catch `sqlalchemy.exc.IntegrityError` around the `create_pending()` call in `InteractionService.execute()` and translate it into a clean `409 Conflict` (optionally with one bounded retry recomputing `next_sequence_number()`, since the retry's own correctness is trivial to reason about — the failure mode is purely "stale sequence number," not an application-level conflict the caller needs to resolve). No schema change required; the `UNIQUE` constraint already does the correctness work.

**Registration:** Not registered in `TECH-DEBT.md` by this audit itself, per `VV-AUDIT-WP-10`/`VV-AUDIT-WP-11`'s own precedent that a V&V Audit does not edit that file directly. Suggested next available ID: **`TD-134`** (Medium, Reliability/Data Integrity-adjacent — but explicitly NOT a `§19.8.5` data-integrity defect, since no data is ever corrupted — Raised In: `VV-AUDIT-WP-12`).
